# Python 版本与优化审查

2026-10-27 审查 Python API、PyO3 直接字段绑定、批量输入工具、wheel/sdist 构建和
测试门禁。发现的问题已修复；本次没有发布到 PyPI，也没有改动提取算法。

## 已修复的问题

### 1. `Article.to_dict()` 对特殊 dataclass 子类不兼容

优化后的方法先读取全部 Article 基础属性，再判断是否应回退 `asdict`。
将继承字段改为 `InitVar` 的合法 dataclass 子类没有该实例属性，因而会报
`AttributeError`，而原有 `asdict` 可以正常工作。

现在先处理子类回退，只有确切的 Article 类型进入标量快路径。保留子类附加字段、
手工传入可变值的深复制、snake_case/camelCase 以及冻结 dataclass 的行为。
新增 `InitVar` 子类回归测试，并保留已有可变字段和子类测试。

### 2. 构建可能使用过期或目标平台不匹配的依赖清单

原 build script 只要求几个清单文件存在；Cargo.lock 更新后仍可能复用旧文件。
现在扩展构建检查锁文件快照：当前所有包块必须存在于准备好的快照中，版本或
依赖变化会拒绝构建，独立 sdist 合法删除无关 workspace 包仍被允许。比较兼容
LF/CRLF，避免 Windows 检出方式导致误报。

目标信息也进入清单。默认准备所有目标的依赖闭包，供跨平台 sdist 使用；显式
单目标 staging 只可用于匹配目标。已对 macOS arm64、Windows x64、Linux x64
三组 Cargo 依赖闭包核对覆盖，构建脚本回归测试验证过期锁文件及错误目标会失败。
这不是宣称已在本机实际构建这三个平台的二进制。

### 3. 版本号分散，且安装包校验可能被 `python -O` 关闭

原版本号分别硬编码在 Cargo、pyproject、Python 模块。现在 pyproject 从 Cargo
读取动态版本，模块从扩展读取版本；安装检查要求 distribution、模块、扩展一致。
CI 安装本轮本地构建产物，不再硬编码发行版本号。

wheel 校验从 `assert` 改为不可被优化模式删除的显式检查，覆盖全部许可证/源码
清单、未列入校验和的文件、重复 ZIP 项、扩展数量及 metadata。回归测试直接以
`python -O` 对损坏 wheel 运行校验，确认不会误报通过。源码包重建后的 wheel
也执行同样检查。

### 4. 源码包提取依赖较新的 Python API，路径校验不足

打包工具曾直接调用 `extractall(filter='data')`，这在早期 Python 3.10 中不可用。
改为共享的受限提取逻辑：先验证完整成员列表，拒绝路径穿越、符号/硬链接、多根、
大小写冲突、Windows 非法/设备路径，再流式写入普通文件。不保留 setuid 等权限。
新增恶意路径、链接、大小写碰撞及普通源码提取测试。

### 5. 畸形批量 JSON 可以使解析窗口持续增长

增量解码器在未完成或无效 JSON 值上会反复读取；只有“每次读取一个小块”并不
构成总窗口上限。现在增加可配置的 `max_value_chars`，默认 32 Mi 个 JSON 文本
字符，超出即失败。合法值后的空白可以增量丢弃，不占用值预算。边界测试覆盖
分块 UTF-8、转义、数字指数、畸形输入、预算触发以及很长的合法空白。

这是仓库基准协议工具的限制，不改变 `extract_html(str, ...)` 的公开 API。
它也不是整个进程的内存限制：输入列表、Unicode 表示和 DOM 仍会占用内存。

### 6. 性能诊断可遗漏样本或在优化模式下跳过校验

配对 worker 现在验证案例顺序、数量、各数组样本数和数值类型；诊断汇总校验
每个重复进程、完整案例集合、每阶段样本数及时间和。相关检查同样不再依赖
可被 `-O` 删除的断言。新增缺失案例、重复/错误重复编号、非加和计时和不完整
worker 输出的负向测试。

已用加固后的汇总器重读已有数据，历史汇总数值保持一致；没有修改原始性能
样本、旧报告或证据包。审查完成后已独立重新运行四语言与同轮三个 Python 版本的性能计时，
结果见 [PYTHON_REVIEW_PERFORMANCE.md](PYTHON_REVIEW_PERFORMANCE.md)；原有测速仍只代表各自历史版本。

## 内存与线程安全检查

没有在本次测试覆盖范围内发现输入所有者泄漏或跨调用 DOM 状态共享。绑定使用
PyO3 管理的不可变字符串引用，Rust 选项在释放 GIL 前转换为独立数据，每次调用
创建自己的解析/提取状态，输出再转换为独立 Python 字段。

原先 `move` 闭包会在 GIL 释放区间销毁字符串所有者；PyO3 本身有延迟引用计数
回收机制，并非已证实的泄漏。现在保留所有者在函数栈上，只借用其数据进入
提取闭包，返回且重新附着 Python 后再销毁，避免不必要的延迟回收路径。

新增测试验证：

- 多线程混合成功、空结果及异常调用后，弱引用输入均可释放。
- 在禁用周期性 Python 字节码线程切换的条件下，原生提取和可读性检测仍能让
  等待的线程执行，确认真正释放了 GIL。
- 原有多线程独立结果一致性测试持续通过。

这些有限测试不证明任意输入都无内存/线程问题。仍未宣称支持 free-threaded
CPython 或 PyPy；普通 CPython 3.10+ 是当前支持范围。元素数限制发生在解析后，
并不约束解析器的瞬时分配；阻塞提取也没有强制取消接口。

## 验证

本机普通 CPython 3.13 / macOS arm64：Python 28 项测试、Rust workspace 测试及
Clippy、wheel 独立安装、sdist 脱离仓库重建再测试通过。完整提取兼容性 604 项、
可读性 282 项均零差异；两个引擎的完整 130 页批量重放输出保持一致。

源码/打包路径和版本测试补进现有 CI。其他操作系统与 Python 版本的 CI 已配置，
本次未声称本机运行过所有矩阵组合。历史性能报告只作为优化前后的既有证据，
审查修复后的新测速与内存复核单独记录在上述复测报告中。
